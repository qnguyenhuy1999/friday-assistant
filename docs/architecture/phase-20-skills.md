# Phase 20: Skills and self-improvement loop

Skills are durable behavioral instructions, never authority. A Skill has a stable key and immutable, SHA-256-checked revisions. Tasks bind ordered Skills explicitly; before the first brain call, Friday persists a `RunSkillResolution` and exact `RunSkillBinding` rows. Retries inherit the frozen bindings, while unresolved historical runs remain unresolved. The runtime injects the frozen instructions in position order under `# SKILLS`, verifies each hash, and fails before a brain call if the complete section exceeds the configured budget.

The normal ToolGateway path is unchanged. Skill text cannot register a tool, change metadata or risk, waive approval, use credentials, alter claims/retries/schedules, or call MCP, computer, filesystem, network, or messaging adapters directly. A malicious instruction may influence a brain proposal, but Friday still validates, classifies risk, obtains any exact tool approval, and owns execution.

Terminal runs materialize one immutable usage record per frozen binding. Records preserve the exact revision, execution lineage, outcome, event-derived counters, and timing. Operators may append bounded helpful/neutral/harmful feedback without altering historical outcomes.

Evaluation suites and ordered cases are persisted independently. The runner snapshots every case and uses only code-owned deterministic evaluators; it has no brain, gateway, filesystem, network, process, MCP, or computer dependency. Candidate evaluations target an inert proposal rather than a production revision and can be compared only with a baseline that has the identical suite snapshot, evaluator version, and runtime fingerprint. The immutable comparison report supplies a recommendation, never an approval.

Friday selects and freezes bounded evidence packages before candidate generation. The Claude CLI adapter invokes its brain-only mode with tools disabled, strict empty MCP configuration, safe mode, and no session persistence. Candidate output must match the strict JSON contract, reference only frozen evidence IDs, differ from the base revision, and remains a `SkillImprovementProposal`; it cannot create or activate a revision.

Promotion is a separate exact-intent transaction. A promotion request binds the proposal, base and current active revisions, candidate hash, comparison report, evaluation ID, and target version in an authorization fingerprint. Approval rechecks every field, creates exactly one generated immutable revision, activates it, consumes the request by marking it promoted, and updates the proposal atomically. A stale request creates no revision. Rollback uses the same exact-binding approach to reactivate an existing revision—never deleting history or copying content.

The worker maintenance loop may evaluate enabled improvement policies. It selects bounded evidence from the active revision's usage and feedback, freezes it, invokes only the brain-only candidate generator outside a transaction, then obtains exact case outputs for the base and candidate from the same brain-only runtime. Friday persists deterministic evaluation runs and the immutable comparison report before moving the proposal to human review. Cooldown is recorded only after that durable work completes. The loop has no promotion authority; human approval remains required for every promotion and rollback.
